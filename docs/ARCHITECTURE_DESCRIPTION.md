# TestBrain 系统架构描述文档

---

## 1. 整体架构概览

### 1.1 项目定位

TestBrain 是一个基于大语言模型的智能测试平台，旨在通过 AI 技术自动化生成、评审和执行测试用例，提升软件测试效率和质量。

### 1.2 架构风格

采用**分层架构**与**微服务思想**相结合的设计模式：

- **分层架构**：清晰分离表现层、控制器层、业务逻辑层、数据访问层和基础设施层
- **模块化设计**：各功能模块独立开发、部署和扩展
- **工厂模式**：LLM服务采用工厂模式实现多模型支持
- **单例模式**：知识库服务采用单例模式确保全局唯一性

### 1.3 核心价值主张

| 维度 | 价值描述 |
|-----|---------|
| 自动化 | 基于LLM自动生成高质量测试用例 |
| 智能化 | AI驱动的测试用例评审和优化 |
| 可扩展 | 支持多种LLM模型和向量数据库 |
| 可追溯 | 完整的测试执行记录和审计日志 |

## 2. 核心组件及其职责

### 2.1 前端展示层 (Presentation Layer)

**职责**：提供用户交互界面，展示测试用例、执行结果和统计数据

**组件构成**：
- **模板视图**：基于 Django Template 的页面渲染
- **API视图**：RESTful API 接口，支持前端异步请求
- **静态资源**：CSS、JavaScript、图标等前端资源

**页面模块**：
| 页面 | 路径 | 功能描述 |
|-----|-----|---------|
| 首页 | `/` | 系统概览和快速导航 |
| 测试用例生成器 | `/test_case_generator/` | PRD文档上传和测试用例生成 |
| 测试案例评审 | `/test_case_reviewer/` | 测试用例AI评审和状态管理 |
| PRD分析器 | `/prd_analyzer/` | PRD文档结构化分析 |
| 接口用例生成器 | `/iface_case_generator/` | 接口测试用例自动生成 |
| Java源码分析器 | `/java_code_analyzer/` | Java代码静态分析 |
| 知识库管理 | `/knowledge/` | 文档上传和向量存储管理 |
| 测试执行管理 | `/test-execution/` | 测试用例执行和结果查看 |
| 系统归属管理 | `/system/` | 系统配置和管理 |

### 2.2 控制器层 (Controller Layer)

**职责**：处理HTTP请求，路由分发，请求生命周期管理

**核心组件**：
- **URL路由**：`config/urls.py` 定义系统所有路由映射
- **视图函数**：处理请求参数、调用业务逻辑、返回响应
- **中间件**：请求预处理、身份验证、日志记录

**请求处理流程**：
```
Request → Middleware → URL Router → View → Model → Response
```

### 2.3 业务逻辑层 (Business Logic Layer)

**职责**：封装核心业务逻辑，实现测试用例的生成、评审和执行

**AI Agent 服务**：

| Agent | 职责描述 |
|-------|---------|
| **测试用例生成Agent** | 根据PRD文档自动生成结构化测试用例 |
| **测试案例评审Agent** | 对生成的测试用例进行AI评审，给出改进建议 |
| **PRD分析Agent** | 解析PRD文档，提取需求要点 |
| **接口用例生成Agent** | 分析接口文档，生成接口测试用例 |
| **Java代码分析Agent** | 分析Java源码，生成单元测试用例 |

**核心服务**：

| 服务 | 职责描述 |
|-----|---------|
| **系统服务** | 系统信息的CRUD操作 |
| **测试计划服务** | 测试计划的创建、管理和执行 |
| **测试执行服务** | 测试用例的批量执行和结果收集 |
| **知识库服务** | 文档的Embedding存储和向量检索 |

### 2.4 数据访问层 (Data Access Layer)

**职责**：数据持久化和检索，支持关系型数据库和向量数据库

**技术组件**：
- **Django ORM**：关系型数据的增删改查
- **MySQL**：核心业务数据存储
- **Milvus**：向量数据存储和相似性检索
- **Sentence Transformer**：文本Embedding生成

**核心数据模型**：

| 模型 | 核心字段 | 业务含义 |
|-----|---------|---------|
| **User** | id, username, email | 系统用户（Django内置） |
| **System** | id, name, code, status | 被测系统信息 |
| **TestCase** | title, description, test_steps, status | 测试用例定义 |
| **TestPlan** | title, description, system_id | 测试计划 |
| **RequirementDoc** | title, content, system_id | 需求文档 |
| **TestCaseReview** | test_case(FK), reviewer(FK), review_comments | 测试案例评审记录 |
| **TestExecutionRecord** | test_case(FK), status, executor(FK), duration, log | 测试执行记录 |
| **TestExecutionBatch** | name, status, test_cases(M2M), executor(FK) | 测试执行批次 |

### 2.5 基础设施层 (Infrastructure Layer)

**职责**：提供底层技术支撑和外部依赖管理

**基础设施组件**：
| 组件 | 用途 |
|-----|-----|
| **MySQL 8.x** | 主数据库 |
| **Milvus 2.4.x** | 向量数据库 |
| **Redis** | 缓存和消息队列（预留扩展） |
| **Logging** | 日志记录系统 |
| **.env** | 环境配置管理 |

## 3. 模块间交互关系

### 3.1 测试用例生成流程

```
用户上传PRD文档
    ↓
文档解析服务 (unstructured/python-docx)
    ↓
知识库检索 (RAG增强)
    ↓
LLM调用 (DeepSeek/Qwen)
    ↓
JSON解析和验证
    ↓
Django Model保存
    ↓
测试用例入库
```

### 3.2 测试案例评审流程

```
待评审测试用例
    ↓
测试案例评审Agent调用
    ↓
评审意见生成
    ↓
测试用例状态更新 (pending → approved/rejected)
```

### 3.3 测试执行流程

```
用户选择测试用例
    ↓
创建执行批次
    ↓
逐个执行测试用例（异步）
    ↓
记录执行状态
    ↓
生成执行结果
    ↓
更新TestExecutionRecord
```

### 3.4 知识库检索流程

```
用户查询
    ↓
Embedding生成 (BGE-M3)
    ↓
向量相似度搜索 (Milvus)
    ↓
返回相似文档
```

## 4. 数据流向

### 4.1 数据流分类

| 数据流 | 方向 | 描述 |
|-------|-----|-----|
| **文档上传流** | 前端 → 后端 → 存储 | PRD/接口文档上传和解析 |
| **测试用例流** | LLM → 解析 → 数据库 | 测试用例生成和存储 |
| **评审数据流** | 数据库 → LLM → 数据库 | 测试用例评审和状态更新 |
| **执行数据流** | 数据库 → 执行引擎 → 数据库 | 测试执行和结果记录 |
| **检索数据流** | 用户输入 → Embedding → 向量库 → 返回 | 知识库查询 |

**测试用例JSON格式**：
```json

  "title": "测试用例标题",
  "description": "测试用例描述",

    {"step": "步骤描述", "expected_result": "预期结果"}
  ],
  "status": "pending",
  "priority": "high",
  "system_id": 1
}
```

**执行记录格式**：
```json
{
  "test_case_id": 1,
  "status": "passed",
  "executor_id": 1,
  "start_time": "2024-01-01 10:00:00",
  "end_time": "2024-01-01 10:05:00",

  "error_message": null

```

## 6. 关键设计决策及理由

### 6.1 分层架构设计

**决策**：采用五层架构（表现层→控制器层→业务逻辑层→数据访问层→基础设施层）

**理由**：
- **关注点分离**：每层职责清晰，便于独立开发和维护
- **可测试性**：各层可独立进行单元测试
- **可扩展性**：便于添加新功能而不影响其他层
- **技术隔离**：底层技术变更不影响上层业务逻辑

### 6.2 LLM服务工厂模式

**决策**：使用工厂模式创建LLM服务实例

**理由**：
- **统一接口**：所有LLM模型使用统一接口调用
- **易于扩展**：添加新模型只需实现接口
- **配置灵活**：运行时可切换不同模型
- **解耦合**：业务逻辑不依赖具体LLM实现

### 6.3 知识库单例模式

**决策**：知识库服务采用单例模式

**理由**：
- **资源共享**：避免重复创建Embedding模型
- **性能优化**：单次加载，多次使用
- **一致性保证**：全局唯一的知识库实例

### 6.4 SSE实时进度推送

**决策**：使用Server-Sent Events实现实时进度推送

**理由**：
- **轻量级**：无需WebSocket的复杂握手
- **单向通信**：适合进度推送场景
- **自动重连**：浏览器自动处理断线重连
- **低延迟**：实时更新执行进度

### 6.5 异步任务执行

**决策**：使用Thread实现异步任务执行

**理由**：
- **非阻塞**：不阻塞前端主线程
- **简单易用**：Python原生支持，无需额外依赖
- **批量处理**：支持大批量测试用例执行
- **资源控制**：可控制并发线程数量

## 8. 扩展性设计考虑

### 8.1 模型扩展

**设计原则**：通过工厂模式实现模型扩展

**扩展步骤**：
1. 在 `apps/llm/` 下创建新模型实现类
2. 继承 `BaseChatModel` 基类
3. 在工厂类中注册新模型
4. 更新配置映射表

### 8.2 功能模块扩展

**设计原则**：模块化设计，独立开发和部署

**扩展步骤**：
1. 在 `apps/ai_agents/` 下创建新模块目录
2. 实现视图、Agent和模板
3. 配置URL路由
4. 注册到系统菜单

### 8.3 数据库扩展

**设计原则**：ORM抽象，支持多数据库后端

**扩展步骤**：
1. 使用Django ORM定义模型
2. 配置数据库路由
3. 生成迁移文件
4. 执行数据库迁移

### 8.4 性能扩展

**设计考虑**：
- **缓存策略**：Redis缓存热点数据
- **异步处理**：任务队列处理耗时操作
- **读写分离**：MySQL主从复制
- **水平扩展**：支持多实例部署

### 8.5 安全扩展

**设计考虑**：
- **身份认证**：JWT/OAuth2支持
- **权限控制**：基于角色的访问控制
- **数据加密**：敏感数据加密存储
- **审计日志**：完整的操作记录

## 10. 总结

TestBrain 架构设计遵循以下核心原则：

1. **分层清晰**：五层架构，职责明确
2. **模块化**：功能解耦，独立演进
3. **可扩展**：支持多种LLM模型和数据库
4. **高性能**：异步处理和实时推送
5. **可维护**：代码结构清晰，文档完善

该架构为测试自动化平台提供了坚实的技术基础，支持未来功能扩展和性能优化。
